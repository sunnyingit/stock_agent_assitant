# 诊断结论：只有一份，由客户端的定时任务产出

状态：设计稿，未实现。依据是 2026-11-07 对代码的梳理（点击路径、定时路径、各层缓存）。

## 1. 要解决的问题

现在有两套分析系统，各存各的，互不知道：

| | A：综合判断（Python） | B：研判群（Go） |
|---|---|---|
| 产出 | 规则版 + 正反方 + 主分析师裁决、价位、走势 | 五位 LLM 分析师的 headline、看多/看空、主分析师卡片 |
| 存放 | `data/synthesis.db` 的 `runs` | Go 数据目录 `groups/<code>.json`、`.debate.json` |
| 谁在用 | 右侧「结论」页、自选副标题、持仓页、通知、战绩、每晚任务 | 中间对话气泡 |
| 谁来更新 | 每晚任务、后台 worker、点击触发的重算 | 只有首次打开或点「重新分析」；之后无限期复用 |

后果：
1. 右侧结论和对话里的主分析师可以互相矛盾（实测一次：对话里 8:0，右侧 3:1）。
2. 每晚任务产出的结论，对话里看不到；对话里的分析师发言，通知、战绩、自选都用不上。
3. A 里的主分析师读到的「五位分析师的话」是规则模板拼的，不是 LLM 分析师的话（Go 的 LLM 结论从不写回 Python）。
4. 默认模式是 `rule`：每晚存下来的是没有主分析师裁决的规则版，右侧会显示「这次主分析师没有给出裁决」。
5. 点击抽屉会触发后台重算，但已打开的页面永远看不到新结果（前端没有刷新）。

## 2. 目标（已定）

1. **结论只有一份。** 右侧结论页、对话里的各位分析师、各分析师抽屉里的结论、自选/持仓/通知/战绩，读的是同一份。
2. **最终结论以客户端定时任务的产出为准。** 用户点击只读、不产生另一份结论。
3. **各分析师抽屉里的结论，就是那位分析师（LLM）在这份结论里说的话**，不再是规则模板。
4. 对话仍然能追问，追问是在这份结论的基础上继续问，不改变最终结论。

## 3. 总体设计

```
定时任务 stock.nightly（每股一个单元，步骤带检查点）
  collect  取事实（各维度详情，沿用现有缓存）
  analyst  五位分析师（LLM）各出一条 headline         ← 调 Go 的分析师，提示词只有一份
  debate   正反方（LLM）读事实表 + 五位的 headline
  chief    主分析师裁决（3 次一致性，沿用现有校验）
  publish  一次性写入「结论包」，之后才对页面可见
  diff     和上一份比，产出 judgment.changed 通知
                      │
                      ▼
              结论包 conclusion（不可变，带 bundle_id）
                      │
   ┌──────────────┬───┴─────────┬──────────────┬────────────┐
 右侧结论页     对话气泡      各分析师抽屉    自选/持仓/通知   战绩
 （全部只读同一个 GET）
```

### 3.1 结论包（conclusion bundle）

一次完整分析 = 一个结论包，**写入后不改**；新的分析产生新的包。页面永远读「最新的、已发布的」那一个。

```json
{
  "bundle_id": "01JD…",
  "ts_code": "002430.SZ",
  "trade_date": "2026-11-06", "session": "close",
  "generated_at": 1793880000000,
  "source": "scheduled | manual | bootstrap",
  "versions": { "policy": "policy-9", "prompts": { "volume_flow": "…", "chief": "prompt-12" }, "model": "…" },
  "facts_hash": "sha256:…",
  "analysts": {
    "sector":      { "status": "ok", "headline": { "text": "", "status": "warn", "status_text": "偏空", "facts": [] } },
    "volume_flow": { "status": "ok", "headline": {} },
    "news":        { "status": "failed", "reason": "model_error", "headline": null },
    "finance":     {}, "fundamental": {}
  },
  "debate": { "bull": { "points": [], "risk": null }, "bear": { "points": [], "risk": null } },
  "chief": {
    "source": "agent | rule", "fallback_reason": "",
    "direction": "bullish", "level": 1, "position": "mid",
    "headline": "", "text": "",
    "adopted": [], "rejected": [], "score": { "bull": 3, "bear": 1 },
    "postmortem": "", "conflict": ""
  },
  "levels": { "down": {}, "up": {} },
  "brief": {}, "trend": {}
}
```

- 存放：沿用 `runs` 表，把 `analysts` 并进 `data`（现在 `data` 里已有 `decision`、`levels_*`、`brief`、`table`）。`bundle_id` = `runs.id`。不新建第二个库。
- 发布：整份在最后一步一次性写入；中间步骤只在调度器的 `job_step` 里，页面看不到半成品。
- 每位分析师有自己的 `status`。某一位失败，不阻塞整份：主分析师按「该维度不可用」继续（现有逻辑已支持），页面上那位显示「这次没有结论」，不回退规则版冒充。
- 主分析师没通过校验退回规则版时，`chief.source = "rule"` 并写明原因，页面明确标出，不和模型版混着显示。

### 3.2 谁能写

只有一个写入口：调度器里的 `stock.nightly`（以及它的手动运行和「首次打开」引导运行，都是同一个任务，只是触发方式不同）。

- 去掉 `worker` 里「点开维度抽屉 → 30 秒后重算」「打开页面 → 过期就重算」这两条旁路。点击只能**请求**一次任务，不能自己算。
- 每晚任务强制用 agent 模式，不受 `SYNTHESIS_MODE` 环境变量影响（没配模型时才是规则版，并标明）。

### 3.3 触发与新鲜度

| 场景 | 行为 |
|---|---|
| 每个交易日 20:30 | 持仓、想买、自选全量重算（优先级：持仓 > 想买 > 自选） |
| 08:30 盘前 | 只对持仓和想买做一次轻量更新（沿用 `market.pre`，但改为入队 `stock.nightly` 的手动运行，不再另走 worker） |
| 用户点「重新分析」 | 入队同一个任务（强制），页面显示进度 |
| 打开一只没有结论包的股票 | 入队「首次打开」运行（最高优先级），页面显示进度；完成后加入「最近查看」名单，7 天内每晚也算它 |
| 盘中 | 不自动重算。页面显示的是「上一个收盘日的结论 + 当前行情」，价位是否被穿过由现有价格提醒处理 |

新鲜度由页面显式告诉用户，不靠猜：
- 结论包带 `trade_date`、`generated_at`、`source`；页面头部写「数据日期 11-06 · 生成于 20:41 · 定时任务」。
- 过期判定（任一成立）：不是最近收盘日；`policy` 或任一提示词版本变了。过期时仍显示旧包，但加一条横幅「结论已过期，今晚 20:30 更新 / 立即重新分析」，并自动入队一次。

### 3.4 读接口

一个接口给所有页面用：

```
GET /api/v1/stocks/{ts_code}/conclusion
→ { "bundle": {…}, "freshness": "fresh|stale", "job": { "state": "none|queued|running", "step": "analyst.news", "progress": [...] } }
```

- 右侧结论页、对话气泡、各分析师抽屉的 headline、自选副标题，全部从这个响应里取。
- `job` 来自调度器的 `task_run` / `job` / `job_step`，用来在页面上显示「正在更新：新闻分析师…」。
- 刷新：任务完成时通过现有的 `/sched/stream`（SSE）或轮询通知页面重新拉；已打开的页面会更新，不再停在旧数据上。
- 原来的 `chief/stream`、`bull/stream`、`bear/stream`、`dimensions/*/stream`（开场用）和 Go 的 `agents/*/stream`，页面不再调用；只剩生产者在内部使用。

### 3.5 对话怎么变

- 中间的「研判群」开场不再现场让五位分析师逐个说话，而是**回放结论包**（保留逐位亮出来的动画，但内容是已经存好的），气泡上标「来自 11-06 20:41 的定时分析」。
- 用户追问：照旧调 Go 的分析师，但把结论包里相关的内容作为上下文（取代现在的群记录文件）。追问的回答只写入对话记录，**不改变最终结论**；页面上标「追问回答」，和「结论」区分开。
- 主分析师「合说」那一问：只总结追问里几位的回答，不再生成新的方向和档位。
- Go 的 `groups/*.json` 降级为追问记录，不再作为结论来源；Go 自己的 `chief/detail` 不再使用。

### 3.6 各分析师抽屉

- 抽屉顶部的「分析师结论」= `bundle.analysts[dimension].headline`，和对话里那位说的是同一条。
- 抽屉下面的数字、图表、规则逐项（体检）仍然是详情接口现算的事实，不属于「结论」；页面上写明「以下是数据和规则读法，不是分析师结论」，避免两者混淆。
- 规则模板的 headline 只在该分析师 `status = failed` 时作为「规则摘要」展示，并明确标注，不当作分析师结论。

## 4. 生产者怎么跑五位分析师

先澄清：Go 服务和 Python 后端都在用户自己的电脑上（Electron 同时起它们，Python 调 Go 走的是本机回环地址），**不管选哪种，都是在客户端跑，不涉及服务端**。真正的问题是：开场那一步该由谁来执行。

Go 里开场的实际过程是：拼系统提示词（`prompt.md` + 规则 + 技能文档 + JSON 约定）→ 调一次 `fetch_facts` 拿事实 → 模型输出一个 JSON → 校验（有没有禁用词、状态合不合法、引用的事实编号是否在目录里且以 `fr.`/`ff.` 这类前缀开头）。开场用不到多步工具循环，五位分析师的开场都只用 `fetch_facts` 这一个工具。

| | Python 调 Go（第一版设计） | **Python 直接跑（改选这个）** |
|---|---|---|
| 位置 | 客户端，Python → 本机 Go | 客户端，全在 Python 里 |
| 速度 | Go 对同一只股票有串行锁，五位依次说，单只约 3 到 4 分钟 | 事实 Python 已经有，五位并行，单只约 1 分钟 |
| 依赖 | 要 Go 在运行；要读 SSE；失败面多一层 | 不依赖 Go |
| 模型配置 | 分析师用 Go 的 `config.yaml`，正反方和主分析师用 Python 的 `.env`，同一个结论里用了两套模型配置 | 全用 Python 的一个网关：同一套模型、重试、token 计数，调度器的预算能精确记账 |
| 失败和重试 | 一个分析师失败往往要整个重来 | 每位分析师是一个步骤，带检查点，只重试失败的那一位 |
| 可测试性 | 要起 Go 服务 | 和现在 decider 的测试一样，用假模型 |
| 风险 | 提示词只有一份 | 提示词拼装逻辑要在 Python 里再实现一份（约 150 行），可能和 Go 的走样 |

我最初倾向「Python 调 Go」，理由只有一条：提示词只有一份、行为和对话里一致。你的问题提醒我，这个理由不够：开场那一步本来就没有工具循环，价值很小，却换来串行、双配置、多一层依赖。所以改成 **Python 直接跑**，并用下面几条把「提示词走样」的风险压住：

1. **提示词文本仍然只有一份**：Python 直接读 `go-harness/web/agents/<id>/prompt.md`、`agent.yaml` 和对应的技能文档；路径由 Electron 通过环境变量 `AGENTS_DIR` 传给 Python（开发时指向相邻目录），安装包里把这些文件随股票后端一起打包。
2. **拼装规则抄 Go 的 `systemPrompt()`，并加测试**：测试里断言 Python 拼出的系统提示词包含同样的 `prompt.md`、规则、技能文档和 JSON 约定；改 Go 的拼装时测试会提醒同步改 Python。
3. **校验用同一套规则**：禁用词（`agent.yaml` 的 `forbid`）、状态取值、事实编号必须在目录里且前缀对得上；没有事实时必须说明没取到。
4. Go 的分析师继续负责**追问**（多步工具、画图），不再负责产出结论。

每只股票大约 10 次模型调用（五位分析师 + 正反方 + 主分析师 3 次）。预算由「分析次数」改成按调用次数和 token 记账；全量 30 只，按 `llm` 队列并发 2 估算，约 1 小时内，落在 20:30 到 24:00 的窗口里。

## 5. 对现有代码的改动

Python（`stock_agent_assitant`）：
1. `service.compute`：新增 `analysts` 入参；`table.headlines` 用 LLM 分析师的 headline，不再用规则模板。事实哈希（用于复用判断）只看事实，不含 LLM 文本，否则每次都因为措辞不同而无法复用。
2. 新增 `app/synthesis/analysts.py`：读 `AGENTS_DIR` 下的提示词和技能文档，拼系统提示词，用 Python 网关各调一次，校验后得到 headline；五位并行。`scheduler/tasks/nightly.py`：任务改成上面的步骤，`analyst.<维度>` 各是一个检查点步骤；`analyze` 里强制 agent 模式；失败的分析师写 `status: failed`，不抛错中断整只股票。
3. `/api/v1/stocks/{code}/conclusion`：新接口；`chief/detail`、`/synthesis` 内部改读同一个结论包（接口先保留，响应里加 `bundle_id`）。
4. 去掉旁路：`worker.notify`（点抽屉触发重算）、`/synthesis` 里的过期重算、`chief/detail` 里的现算；全部改为「入队任务」。
5. `analyst_concl` 键值存储和 Python 的开场 `stream` 端点：保留一个版本，只给生产者降级使用，随后删除。

Go（`go-harness`）：
1. 追问接口接受「结论包」作为上下文；群记录只存追问。
2. 开场那条路径（`agents/{id}/stream` 做开场）不再被页面调用，先保留，稳定后删除。

前端（`index.html`）：
1. 对话区：开场改为回放结论包；不再自己发起五位分析师和正反方的请求；加「定时分析 · 日期 · 生成时间」标识和过期横幅。
2. 右侧结论页和各抽屉：全部从 `/conclusion` 取；任务进行中显示步骤；完成后自动刷新。
3. 「重新分析」：改为请求入队 + 显示进度。

## 6. 迁移与风险

分三步，每一步都可以单独上线、可回退：
1. **后端结论包 + 接口 + 任务步骤**（页面暂不变）：先让每晚任务产出完整的结论包，和现有结果并存比对。
2. **前端改读结论包**：右侧结论页、抽屉、对话回放。此时开始只有一份。
3. **清旁路**：删除 worker 的点击触发重算、Go 群记录当结论的用法。

风险：
- 定时任务产出慢或失败，页面就是旧的。所以必须有进度显示、过期横幅、失败时保留上一份并明确标注，不能让页面空着。
- 首次打开一只新股票要等 3 到 4 分钟（比现在对话逐位发言慢不了多少，但现在是边说边看，回放则要等整包发布）。折中：首次引导运行时，每位分析师说完就写入 `job_step` 并在页面上先显示，主分析师等整包发布。
- 找不到提示词文件（`AGENTS_DIR` 没设或安装包没带）时，分析师步骤整体失败；此时整包标记 `analyst failed`，主分析师仍按规则版和可用维度出结论，并明确标「分析师未运行」。启动时就检查并在日志和收件箱里报。
- 数据口径：结论是「上一个收盘日」的，盘中价格变了，页面要把当前价和价位的关系标出来，避免用户以为结论是实时的。

## 7. 验收

- 同一只股票，在右侧结论页、对话里的主分析师、自选副标题、战绩里看到的方向和档位完全一致（同一个 `bundle_id`）。
- 点击任何地方都不会产生新的结论，只会读取或入队。
- 每晚任务跑完后，已打开的页面自动更新，不需要刷新。
- 任一分析师失败时，那一位显示「没有结论」，其他不受影响，主分析师标明缺了谁。
- 抽屉里的分析师结论与对话里那位说的逐字一致。

## 8. Python 后端部署到远程之后：远程只出事实，本机出结论（2026-11-07 修订，已定）

> 上一版的第 8、9 节把「分析师和结论」也放到了远程、由运营方出模型钥匙。这和一开始的决定（LLM 在客户端、用用户自己的钥匙、服务端不跑 LLM、客户端的定时任务产出的结论为最终结论）相反，已撤回，下面是按原决定重写的版本。

### 8.1 谁做什么

| | 远程（server profile） | 本机（client profile） |
|---|---|---|
| 跑什么 | **只跑事实，不碰模型**：五个维度的确定性详情、日线和资金流等对齐数据、市场快照、公告和新闻的原始条目（规则分类）、交易日历、就绪标记 | **分析师（LLM）、正反方、主分析师、结论包、战绩、通知、个人数据** |
| 定时任务 | `stock.details`（新，订阅并集预热）、`market.publish`、`news.collect`、`ready.probe`、`server.purge` | `stock.nightly`（产出结论包）、`alerts.*`、`notify.*`、`relay.sync`、`watchdog`、`maintenance` |
| 数据 | `server.db`（共享产物），没有任何用户私有数据，没有结论 | `synthesis.db`（结论、战绩、走势）、`holdings.db`、`notify.db`、`scheduler.db` |
| 模型钥匙 | 不需要 | 用户自己的 |

结论只有一份的含义是：**一台客户端上只有一份**，由它自己的每晚任务产出，页面和对话都读它。

### 8.2 这样做的好处和代价

好处：
- 运营方没有模型成本，也不需要为模型调用担责；和原来的隐私、多用户、钥匙决定一致。
- 个人数据可以用在分析里（比如结合持仓给提示），不必出本机。
- 本机的 `synthesis.db` 本来就是结论、战绩、自选、提醒放在一起，**不需要拆库**（上一版要拆是因为把结论放到了远程）。
- 远程只剩确定性的东西：可缓存、可按哈希复用、可预热，和已经做好的 `app/server` 一致。

代价（需要接受）：
- 每个用户自己跑一遍分析：每只股票每晚约 10 次模型调用，成本在用户自己的钥匙上，共享不了。
- 同一只股票在两台设备上的结论可能不同（模型有随机性）；战绩也是各人的，汇总不了。
- 客户端没开机时当晚的分析会延后，由调度器的补跑规则在下次开机时补上；打开一只没有结论的股票要等本机现算。
- 本机必须带 Python 后端（安装包里目前还没有）。

### 8.3 流水线在哪里切开

现在 `load_table` 把「取数」和「装表」写在一起。要拆成两段：

1. **取数（远程）**：`collect` 里五个维度的 `build_detail`、`load_aligned`，以及对应的确定性部分。产物放进服务端 `artifact` 表：`kind=stock.details`，`subject=ts_code`，`as_of=交易日`，内容是五个维度详情 payload + 对齐数据（日线、资金流、板块、指数、融资分位）。
   - **新闻维度不能在远程调模型：** `news_detail` 现在遇到有模型时会调 LLM 抽取事件。远程跑的版本关掉模型，只返回清洗后的新闻条目和规则分类（`announcements.enrich` 那一套）；LLM 抽取事件留给本机，用本机的钥匙做。
2. **装表和分析（本机）**：`fr.*`/`ff.*`/`fd.*`/`sp.*` 这些事实表、`Evaluator`、价位候选、事实表、分析师、正反方、主分析师，全部在本机从产物起步。拿不到远程产物时用本机缓存的上一份，并标「事实已过期」。
3. 现有的 `stock.facts` 产物（只含事实表）保留给轻量用途；分析用 `stock.details`。

### 8.4 生产者（本机）

- `stock.nightly` 的步骤：拉 `stock.details`（ETag/304）→ 本机装表 → 五位分析师（Python 直接跑，并行）→ 正反方 → 主分析师（3 次一致性）→ 发布结论包 → 对比上一份发判断变化通知。
- 分析师提示词归本机后端所有，随安装包一起带；开场提示词和 Go 的追问提示词分开。不再需要 `AGENTS_DIR` 跨仓库依赖。
- 触发、新鲜度、读接口、对话回放、抽屉：沿用第 3 节，只是「读」的是本机后端，不是远程。
- 强制模型版不受环境变量影响；没配模型钥匙时是规则版并明确标注。

### 8.5 远程的要求

- HTTPS、设备令牌（`app/server/security.py` 已有）、每设备限流；页面里的共享接口（市场页、各维度详情、`stock.details`）和 Go 的 `fetch_facts` 都带令牌；`STOCK_API_BASE` 已可配。

## 10. 重新划分：客户端不带 Python（2026-11-07，取代第 8、9 节里「Python 在客户端」的部分）

### 10.1 为什么改

把 Python 后端打进客户端安装包，包会很大，也要在用户机器上管理两个进程。改成：服务端出所有确定性的东西和消息推送，客户端是 Go + Electron，自己做定时任务、分析师和个人数据。

### 10.2 分工

| 数据 | 取数；各维度详情和事实表（现有 `/api/v1/stocks/<code>/dimensions/<dim>/detail`，资金流、财报、基本面、板块的「体检」都是纯规则）；新闻采集和规则分类；市场页（所有人看同一份）；价位候选 | 持仓、自选、聊天记录、结论包、收件箱，只存本机 |

## 13. 扫描页：每天的预测和战绩（2026-11-07 夜）

设计稿是「桌面客户端 · 每日扫描（AI 预测与战绩）」。已定（用户选的第一种）：**扫描的范围只有你自己的自选、持仓、想买**，用现成的夜间任务；不做全市场候选池（以后要做，把候选名单塞进夜间任务的扇出就行）。

**一条预测是什么：** 每份结论（夜间任务出的，或你在诊断页点「重新分析」出的）记一条，只追加，不能改。字段：股票、来源（`scan` 定时扫描 / `diagnose` 你诊断）、方向（偏多/偏空/不明，来自主分析师的裁决）、强度（稍微/比较明显/明显）、主要依据（裁决文字的第一句）、起点价（发出时最近一个收盘价）、板块、市场环境（上涨市/震荡市/下跌市）、各位分析师当时的倾向。同一份结论同一来源只记一次。放 `<DataDir>/client/predictions.json`。「不明」记下来但不结算，计入不明率。

**怎么结算：** 任务 `scan.settle`，交易日 17:30，要等当天日线到了（没到就 `NotReady` 20 分钟后再来）。第 5、20 个交易日各结算一次（按股票自己的日线数，不依赖休市日历）。比的是本股涨幅减所在板块涨幅（申万二级，没有用一级；板块指数序列来自 Python `/shared/sector-series/<code>`）：偏多且超额 > 0.5 个点算对，偏空且超额 < −0.5 算对，之间算持平，不计入命中率。起点价本股和板块都用发出时最近一个收盘价，所以不需要 09:35 的开盘价任务。结果也只写一次。结算后在收件箱写一条「战绩结算」，可推到企业微信等渠道。

**为什么错了：** 不让模型事后编。错的预测按模板：找当时和最终方向一致的分析师，说「某某分析师偏多（他的依据），但 5 天后本股跑输板块 x 个点」，并记下是哪一维；「准不准」里按维度算命中率。

**「准不准」怎么算：** 命中率 = 对 ÷（对 + 错）；「随便选」= 每次都押同一方向的命中率（取多数方向）；比它高多少个百分点才叫有用。按来源、强度、方向、市场环境、分析师拆开；样本少于 20 条的行显示「样本不足」；强度「比较明显」和「稍微」差不到 2 个点时页面会直接说「强度没有区分度」。

**接口（Go，`/api/scan/*`）：** `summary`、`today?source=`、`tracking?due=&mine=&source=`、`settled?horizon=&source=&range=&wrong=&q=`、`accuracy?horizon=&days=`、`export.csv`。页面 `web/static/scan.html`（四个页签：今日预测、跟踪中、已结算、准不准；通知抽屉复用持仓页的 `/api/v1/holdings/notifications`，「战绩」页签里是结算通知）。侧栏「扫描」入口在市场、诊断、持仓三个页面都接上了。

**和我有关：** 来自本机的持仓、想买、自选；AI 偏空而你持有/想买的会标「AI 偏空，和你的打算不一致」。

**「即将执行的定时任务」（今日预测页签顶部，`GET /api/scan/upcoming`）：** 列出下一次夜间任务和结算任务的时间（周末、休市日自动跳到下一个交易日）、上次执行结果、夜间任务会扫哪几只（持仓 → 想买 → 自选，各自现有结论的时间和方向）、接下来几天有多少条预测到期，「盯价」（你设的到价提醒：现价、还差多少、下一次什么时候检查，可以在这里撤掉；开了离线转发会注明）、以及折叠起来的其他定时任务。还没有任何预测时它排在空态提示前面。两个扫描任务各有一个「现在跑一次」按钮（`POST /api/scan/run`）：夜间任务会给每只股票各跑一遍，今天已经有结论的直接按它生成的时间记成预测、不重新调模型，没有的才调模型；结算任务立刻对账一遍。从按钮触发的预测来源标「定时扫描」。夜间任务遇到今天已有的结论时也会补记预测（以前直接跳过，所以旧程序生成的结论没被记下来）。

**没做 / 要知道**

**「提醒我」和定时任务的关系（2026-11-07，设计结论，部分已做）：** 一次「提醒我」只增加一条订阅（价格提醒、规则），不为它单独建定时任务；同一类的订阅由一个共用的盯盘任务每轮一起读（价格 → `alerts.intraday`/`alerts.close`，公告 → `news.watch`，日历 → `calendar.morning`，涨跌停/资金流 → `signals.close`）。任务跑完不为「没事发生」写通知：有命中才产出事件进收件箱（已有去重和免打扰），任务本身跑没跑过由安静的运行回执证明，失败才弹通知。有日期的提醒（披露日、解禁日）才适合做成一次性待办，放在通知抽屉的「即将发生」里，到点或过期自动消失。已做：扫描页的「盯价」；诊断页「要盯的两个价」和「如果我错了」里的「到了提醒我」按钮真正存提醒了（`POST /api/v1/stocks/{code}/alerts`，再点一次 `DELETE`，打开结论面板时读回已设的状态；价位条件写「收盘…」的按收盘确认，其余盘中触及就提醒）。在这之前这个按钮只改页面里的一个变量，刷新就没了，也没有任何提醒被存下来。没做：针对某条新闻/公告/披露日的「提醒我」按钮，以及「即将发生」里的一次性待办。
